## AI × Web3 问题地图与主方向选择

> 📊 **可视化图表**: [ai-web3-problem-map.html](./ai-web3-problem-map.html)

### 一、问题地图（5 个方向）

**① Payment / Commerce / Settlement**

- AI 作用：评估支付合理性（是否值得付、付多少、何时付）
- Web3 机制：提供 Agent 可独立使用的链上支付通道（地址即账户，不依赖法人实体）

**② Identity / Reputation / Capability ← 主线**

- AI 作用：评估 Agent 的信誉和能力（读取历史记录 → 输出可信度判断）
- Web3 机制：链上存储不可篡改的身份注册（DID）和行为记录，任何人均可验证

**③ Wallet / Permission / Safe Execution**

- AI 作用：动态判断每笔交易的合理性（上下文感知的风险评估）
- Web3 机制：智能合约提供可编程权限（限额、白名单、时间锁），hard constraint 兜底

**④ Privacy / Security / Sovereignty**

- AI 作用：判断什么信息该公开、什么该保密（隐私策略引擎）
- Web3 机制：zk-proof 等技术在不泄露具体内容的前提下完成合规验证

**⑤ Dev Tooling / Agent Workflow**

- AI 作用：生成 Agent 的能力、训练新技能、让 Agent 持续学习和适应
- Web3 机制：提供公开可验证的部署和调用基础设施（Agent 像合约一样透明可审计）

### 二、两个方向的深入分析

**方向 ②：Identity / Reputation / Capability**

为什么不是纯 AI 问题？

- AI 可以分析行为数据、输出信誉评分——但数据本身从哪来？如果是某家公司维护的中心化数据库，那家公司可以修改、删除、关闭服务
- 信誉评估的有效性依赖于原始数据的真实性。没有不可篡改的数据源，AI 的输出就是"garbage in, garbage out"
- 这是一个数据层的问题，AI 自己解决不了

为什么不是纯 Web3 问题？

- 链上可以存原始行为记录，但记录本身不会"说话"
- 一笔交易哈希 + 时间戳对机器来说只是数字，把这个翻译成"这个 Agent 靠谱程度 87%"需要非结构化的分析和推理——这是 AI 的事
- 链上合约只能处理 if-then 确定性逻辑，处理不了信誉这种模糊、动态、依赖上下文的判断

为什么需要结合？

- Web3 提供不可篡改的"证据层"——Agent 做了什么、结果如何，全部上链，任何人可查
- AI 提供"理解层"——把证据翻译成人类和系统能用的信誉信号
- 最终的信任不是信 AI 也不是信链，是信"AI 分析的是链上真实数据"这个闭环

**方向 ⑤：Dev Tooling / Agent Workflow**

为什么不是纯 AI 问题？

- AI 框架（LangChain、AutoGPT 等）解决了"怎么造 Agent"，但没解决"造出来放哪"
- 部署在私有服务器上 = 用户看不到代码、不信任、无法审计。Agent 是个黑盒
- AI 自己解决了能力问题，解决不了可信性问题——而可信离不开部署方式的透明

为什么不是纯 Web3 问题？

- 合约部署的传统范式（编译 → 审计 → 部署 → 调用）处理的是确定性程序
- Agent 是非确定性的：同一个输入不同时间可能不同输出。合约的那套验证框架不直接适用
- 需要定义 Agent 层面的"ABI"——Agent 的能力声明接口、输入输出规范、调用方式——这些设计本身需要理解 AI 的工作方式

为什么需要结合？

- 目标是让 Agent 像智能合约一样：代码公开、逻辑可审计、接口可调用、部署后可信任
- AI 负责 Agent 的"智能"部分，Web3 负责 Agent 的"可信"部分
- 最终形态：一个 Agent = 公开的能力声明（AI）+ 可验证的部署和调用（Web3）

---

### 三、主方向选择

选择 **② Identity / Reputation / Capability** 作为 Week 2 主线。

理由：
- 这是 AI × Web3 最底层的信任基座——无论 Agent 要支付、要执行、要保护隐私，第一步永远是"你知道你在和谁交互"
- 与产品研究方向天然契合：解决的是"标准"和"体验"问题，而不是底层密码学实现
- 后续可以延伸：Agent 的能力声明标准长什么样？用户可以怎么发现和筛选 Agent？如何设计一个"Agent 黄页"？
