# Week 1｜AI × Web3 最小交叉流程图

**任务：** 画出 AI × Web3 最小交叉流程图
**选题：** AI 辅助完成一次测试网合约交互（部署 + 调用）
**复用经验：** Sepolia 测试网交易 + SimpleStorage 合约部署

---

## 流程总览

```
用户想部署/调用一个合约
  │
  ▼
AI 生成操作说明（拆步骤、提醒风险、解释每步意义）
  │
  ▼
人工复核（检查网络、合约地址、交易内容、授权范围）
  │
  ▼
钱包签名（MetaMask 确认 → 签名后交易广播）
  │
  ▼
测试网执行（链上打包、状态变更）
  │
  ▼
区块浏览器验证（Etherscan 查 tx hash / 合约地址）
  │
  ▼
记录 Proof-of-Work 到 GitHub
```

---

## 各阶段详解

### 阶段 1：用户发起任务

**谁执行：** 用户
**发生了什么：** 用户想在测试网上部署一个 SimpleStorage 合约，或调用已有合约的 set() 函数

**AI 能做什么：**
- 解释目标（"部署合约"是什么意思、链上会发生什么）
- 提醒前置条件（需要 MetaMask、需要 Sepolia 测试币）

**AI 不能做什么：**
- 不能替用户决定是否执行
- 不能替用户发起交易

---

### 阶段 2：AI 生成操作说明

**谁执行：** AI（LLM + Prompt + Context）

**AI 的工作：**
1. 拆解步骤：打开 Remix → 编译合约 → 连接 MetaMask → 切换 Sepolia → 点 Deploy 或调用 set() → 确认交易 → 到 Etherscan 验证
2. 解释每步意义（不只是操作指令，而是讲清楚"为什么需要这一步"）
3. 提醒风险点（选错网络、合约地址错误、授权范围过大）

**关键理解：**
- AI 基于 Prompt（任务说明）+ Context（用户已有经验、测试网交易记录、合约代码）生成操作说明
- 说明是"候选建议"，不是"最终命令"
- AI 可能幻觉（hallucination）——生成错误的合约地址或错误步骤

**风险点：**
- AI 可能生成错误的合约地址
- AI 可能遗漏关键步骤（如忘记提醒切换测试网）
- AI 可能解释不清楚，导致用户误解操作意义

---

### 阶段 3：人工复核

**谁执行：** 用户（人工确认）

**复核内容：**
1. **网络检查：** MetaMask 当前网络是不是 Sepolia？（不是主网、不是其他测试网）
2. **合约地址检查：** 要部署或调用的合约地址是否正确？
3. **交易内容检查：** set() 的参数是什么？是不是用户想写入的值？
4. **授权范围检查：** 这笔交易是否需要授权？授权额度是否合理？
5. **Gas 费检查：** Gas 是否在预期范围内？

**为什么必须人工复核：**
- AI 可能犯错（幻觉、信息过期）
- 签名一旦广播，交易不可撤销
- 测试网无风险，但主网上会直接损失真金白银

**关键理解：**
> 这是整个流程中最重要的边界——AI 可以解释、可以建议，但**签名的决定权必须在人手里**。

---

### 阶段 4：钱包签名

**谁执行：** 钱包（MetaMask）

**发生了什么：**
1. 用户点击 Deploy 或 set() 后，MetaMask 弹出确认窗口
2. 窗口显示：交易详情（to、data、gas、value）
3. 用户点击"确认"→ MetaMask 用私钥签名 → 签名后的交易被广播到网络

**关键理解：**
- 签名 = 私钥加密授权 = "我同意这笔交易"
- 签名后交易被广播到全网，不可撤销
- AI 不能替用户签名——签名需要私钥，私钥只在用户的钱包里

**风险点：**
- 如果用户没看清交易详情就签名，可能签署恶意交易
- 如果 MetaMask 弹窗要求"无限授权"，可能带来资产风险

---

### 阶段 5：测试网执行

**谁执行：** 区块链网络（Sepolia 测试网）

**发生了什么：**
1. 交易被网络节点接收
2. 矿工/验证者打包交易进入区块
3. 合约状态变更（如 storedNumber 从 0 变成 42）
4. 产生交易哈希（tx hash）和 Gas 消耗

**关键理解：**
- 交易不是"即时"的，需要等区块确认
- 即使是测试网，也会消耗 Gas（测试币）
- 测试网无真实资产风险，但主网会直接消耗真金白银

---

### 阶段 6：区块浏览器验证

**谁执行：** 用户（通过 Etherscan 验证）

**验证内容：**
1. **交易是否成功：** Etherscan 显示 Status: Success
2. **from/to 是否正确：** 发送方和接收方地址是否符合预期
3. **Gas 是否合理：** 实际消耗是否在预期范围内
4. **合约地址是否存在：** 部署后合约地址是否有效
5. **状态是否真的变化：** 调用 set(42) 后，get() 是否返回 42

**为什么不能只相信 AI 或 Remix 的显示：**
- AI 可能幻觉（声称成功但实际失败）
- Remix 可能显示"成功"但链上实际状态不同
- 只有 Etherscan 是"链上真相"

**关键理解：**
> 区块浏览器是"链上真相的来源"——AI 的输出只是候选结果，链上状态才是最终验证。

---

### 阶段 7：记录 Proof-of-Work

**谁执行：** 用户（通过 GitHub 记录）

**记录内容：**
1. 交易哈希（tx hash）：`0x3875a5b77e029dbc735f376030e19c6668b0621b8db735f6d0869c915f5ab092`
2. 合约地址：`0x80ac7a484a4759ccae47f735e12997361b58658f`
3. Etherscan 链接：https://sepolia.etherscan.io/tx/0x3875a5b77e029dbc735f376030e19c6668b0621b8db735f6d0869c915f5ab092
4. 操作理解和风险点记录

**关键理解：**
- Proof-of-Work 是公开可验证的证据（GitHub + Etherscan）
- 不只是"我做了"，而是"这是我在链上/公开可查的结果"

---

## 总结：AI × Web3 的最小安全链路

```
AI 生成说明（候选建议）
  → 人工复核（检查边界、决定是否执行）
  → 钱包签名（私钥授权、不可撤销）
  → 链上执行（区块链共识）
  → 区块浏览器验证（链上真相）
  → GitHub 记录（公开证据）
```

**核心原则：**
- **AI 是推理层，不是真相源** — 输出是候选结果，不是最终验证
- **Prompt 是软约束，不是安全边界** — 真正的边界由代码、权限、校验和审计承担
- **签名的决定权必须在人手里** — AI 不能替用户签名、授权、付款
- **链上状态是最终真相** — AI 的输出、UI 的显示、用户的判断，都要回到区块浏览器验证

---

## 风险点汇总

1. **AI 幻觉：** 生成错误的合约地址、错误步骤、错误解释
2. **选错网络：** MetaMask 切到主网，实际消耗真金白银
3. **合约地址错误：** 部署到错误地址或调用错误合约
4. **授权范围过大：** 无限授权导致资产风险
5. **只看 UI 不看链：** Remix 显示"成功"但链上实际失败
6. **忽略区块浏览器验证：** 只信 AI 回复，不查链上状态
